## 1. Executive Summary & Vision

The **Deterministic Traceability, Review & Knowledge Consistency Layer** (`010-deterministic-traceability-review`) extends `llm_wiki_ext4vsc` and its native Rust engine (`llm-wiki-core`) to establish a verifiable, bidirectionally traceable bridge between:
1. **Markdown Knowledge Structure** (documents, AST sections/anchors, frontmatter metadata);
2. **Canonical Knowledge Graph** (nodes, reference edges, topology);
3. **Repository Source Code** (code files, paths, explicit dependencies);
4. **Git Version History & Diffs** (working tree, commit deltas, PR/CI branch diffs).

### Foundational Invariants & Architectural Principles
- **Strict Determinism (Constitution Invariant III & IV)**: The engine answers all impact and review queries using explicit, bit-exact rules executed locally in Rust. External LLMs, stochastic classifiers, and probabilistic embeddings are **strictly out of scope** for semantic decision-making.
- **Git as Source of Truth (Constitution Invariant I & II)**: Persistent graph state reflects committed history. Pre-commit/CI evaluation operates on ephemeral candidate deltas without polluting persistent data.
- **Tri-State Lifecycle Separation**: A code modification is not automatically proof of documentation obsolescence. The system formally distinguishes:
  - `change_detected`: A source code file has been created, modified, renamed, or deleted.
  - `review_required`: A documentation note explicitly depends on the modified code and must be examined.
  - `rule_violation` (Drift): An observable fact violates an explicit, machine-verifiable rule (e.g. broken path, cyclic dependency, prohibited dependency).
- **Audit-First Engineering**: Prior to introducing new data structures, existing AST visitors, code citation extractors, and reverse impact indexes are audited and extended rather than replaced.

### User Story 4 - Explicit Rule Verification vs. Semantic Drift Separation (Priority: P2)

As a software architect, I want the engine to evaluate explicit architectural rules (e.g. prohibited component dependencies, mandatory canonical doc links) and produce `rule_violation` findings only when concrete evidence exists, while returning `review_required` or `not_verifiable` when no explicit rule covers the change.

**Why this priority**: Prevents false alarms and tool skepticism. Adheres to Section 9 of the specification: code modification aciona revisão, mas não comprova automaticamente drift arquitetural.

**Independent Test**: Define an architectural rule in `.context-vault.yaml` prohibiting `extension` from depending directly on `crates/core/src/ast`; trigger a git diff introducing this forbidden dependency; verify that the engine emits a deterministic `rule_violation` with exact AST/citation evidence.

**Acceptance Scenarios**:
1. **Given** a code change that violates an explicit rule declared in `.context-vault.yaml` (e.g. `prohibited_dependency`), **When** analyzed, **Then** the engine outputs a finding with category `rule_violation` and full source evidence.
2. **Given** a code change in a business logic function with no violated architectural constraints, **When** analyzed, **Then** the engine outputs `review_required` for declaring docs, never asserting unverified semantic drift.
3. **Given** a prose change where semantic accuracy cannot be mathematically deduced from AST or Git, **When** queried, **Then** the engine classifies the evaluation as Epistemic Tier D (`not_verifiable`).

## 6. Success Criteria *(mandatory)*

- **SC-001 (100% Impact Recall)**: For any committed or staged change to source code files, 100% of documentation notes declaring dependencies on those files (via frontmatter or inline links) are correctly identified in the impact report.
- **SC-002 (PR/CI Gating Reliability)**: In CI workflows, PRs with code changes affecting documented areas without documentation edits or `reviewed_unchanged` receipts are deterministically flagged as `pending` within $\le 100\text{ ms}$.
- **SC-003 (Zero False Positives on Drift)**: Modifying a code file without violating an explicit architectural constraint NEVER produces a `rule_violation` error, maintaining a strict distinction between `review_required` and `rule_violation`.
- **SC-004 (Strict Path Safety)**: 100% of path traversal attempts (`../`) in frontmatter `code_dependencies` or inline links are caught and safely rejected without escaping the workspace root.
- **SC-005 (Graph Integrity Guarantee)**: The persistent knowledge graph is never mutated by working-tree edits or external spike evaluations, preserving Invariant I and Invariant II at 100% compliance.
- **SC-006 (Spike Isolation)**: The Graphify / Understand Anything evaluation spike runs in an independent binary harness, producing an empirical evaluation report without adding runtime dependencies to `llm-wiki-core` or `extension`.

## 7. Assumptions & Boundaries

1. **Tokenization Standard**: All token accounting uses OpenAI `cl100k_base` via `tiktoken-rs` per Constitution Principle I. Any estimations must explicitly state the tokenizer used.
2. **File Granularity First**: Code dependencies are tracked at file-path granularity initially; AST function/class symbol level tracking remains an optional refinement for subsequent phases.
3. **No External Models**: Laya, OpenAI, Claude, or local LLMs are strictly forbidden from participating in the deterministic decision path.
4. **Brownfield Compatibility**: Existing repositories without `code_dependencies` frontmatter function normally; reverse impact falls back to inline markdown code citations.
5. **No Double-Truth**: Frontmatter `code_dependencies` is the canonical per-document declaration; central manifests are only used when documents lack frontmatter capability.
